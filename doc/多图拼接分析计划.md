# 多图拼接分析（单题跨多张）实施计划

> 版本：v1.1　|　日期：2026-10-14　|　状态：M1/M2/M3 已完成（2026-10-15 实现）；最大张数约定为 5
> 目标：解决「一道题不在一张纸/一张照片上，需要多拍几张上传后合并成完整一道题再识别」的问题。

---

## 1. 背景与目标

### 1.1 现状问题

当前所有上传/识别入口都只支持**单张图片**：

| 环节 | 现状 | 位置 |
|---|---|---|
| Web 上传 | `useDropzone({ maxFiles: 1 })`，只选 1 张 | `src/components/upload-zone.tsx` |
| Web 工作流 | 单图 → 题目定位(detect) → 裁剪 → 识别 | `src/components/upload-workspace.tsx` |
| 分析接口 | 只收单个 `imageBase64` | `src/app/api/analyze/route.ts` |
| AI 服务层 | `analyzeImage(imageBase64: string, ...)` 单图签名 | `shared/src/ai/types.ts`、三个 provider |
| 小程序端 | `uni.chooseImage({ count: 1 })` | `uniapp/src/pages/analyze/analyze.vue` |
| 唯一"多图"接口 | OpenClaw 批量上传，但**逐张独立识别、每张单独建错题**，不合并成一道题 | `src/app/api/openclaw/batch-upload/route.ts` |

因此「多图拼接成一道完整题目」目前**完全未实现**，属于全新功能。

### 1.2 目标

- 用户对**一道题**连续拍多张（如题干在第一张、后续问/图在第二张，或长题一页拍不下），
  上传后系统把它**合并成一张完整题目图**，作为**一道题**整体识别、校对、保存。
- 只传 1 张时，走原有单图 + 题目定位 + 框选流程，**行为完全不变**（兼容回归）。

### 1.3 非目标（首版不做）

- 多张照片分别识别成多道题再合并（那是"批量录题"，与 OpenClaw batch 场景重合，不在本次范围）。
- 拼接图内再次按题号框选多题（留作后续增强，见 §7）。
- 横向拼接、自动消除接缝内容等高级拼接（首版只做纵向无缝拼接，见 §4）。

## 2. 需求范围

### 2.1 用户场景（核心）

> 小明拍一道压轴大题，题目跨了两页。他先拍第 1 页（题干），再拍第 2 页（第(2)(3)问 + 配图），
> 两图一起上传 → 系统纵向拼成一张长图 → 识别出一整道题 → 校对保存。详情页「原图」显示拼接后的完整图。

### 2.2 功能需求（FR）

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-1 | 多选图片 | 一次选 2~5 张（默认上限 5，可配置），只选 1 张保持旧逻辑 |
| FR-2 | 预览与管理 | 缩略图列表：查看、调整顺序、删除、追加（继续拍照补图） |
| FR-3 | 合并识别 | 多张按顺序纵向拼接成一张图，直接整体识别（跳过题目定位/框选） |
| FR-4 | 校对与保存 | 校对页展示拼接后的完整原图，保存时以拼接图作为 `originalImageUrl` |
| FR-5 | 错误提示 | 张数超限、单图过大、拼接后总高/体积超限时给出明确提示 |
| FR-6 | 兼容回归 | 单图路径（detect/框选/识别）零变化 |

### 2.3 数据约束（建议默认值，全部可配置）

| 项 | 建议值 | 理由 |
|---|---|---|
| 最大张数 | 5 | 覆盖绝大多数跨页场景；超 5 张说明应分开录 |
| 单张图片上限 | 5MB（解码后） | 对齐 OpenClaw batch 的 5MB 校验 |
| 拼接统一宽度 | 1400px | 兼顾清晰度与 token 消耗 |
| 拼接后最大总高 | 12000px | 浏览器 canvas 与视觉模型 tile 预算的安全线 |
| 拼接后最大体积 | 8MB（解码后） | 分析接口 base64 上限（12M ≈ 9MB）内留余量 |
| 拼接方式 | 纵向，白底，无缝 | 卷面阅读顺序自然 |

## 3. 方案选型

### 3.1 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 服务端拼接（sharp）** ⭐ | 前端只负责多选/排序/预览，把 `images[]` 交给后端；后端用 sharp 纵向拼接后喂给现有 `analyzeImage` | ① 跨端一致（Web/uniapp/小程序共用同一接口）；② 规避浏览器 canvas 最大尺寸与 EXIF 旋转问题；③ AI 层/provider 零改动，风险最小；④ 拼接逻辑只写一份 | 需要新增一个后端合并步骤；raw 图上传带宽略增 |
| B. 前端 canvas 拼接 | 浏览器/uni-app 内用 canvas 拼完再传单图 | 后端零改动 | 各端 canvas API 不同要写两遍；小程序 canvas 尺寸/EXIF 坑多；大图易触发 canvas 上限 |
| C. 多图多模态直传 | 改 `analyzeImage` 签名支持多图，直接给模型多张图 | 不丢图、模型多图理解最好 | 要改 3 个 provider + 类型 + 日志 + 限流，工作量与回归风险最大；当前调用方众多 |

### 3.2 推荐：方案 A（服务端 sharp 拼接）

理由：

1. **AI 链路零改动**：合并后仍走现有 `analyzeImage(单图)`，三家 provider 不用动，detect/校对/保存逻辑全部复用。
2. **一份拼接代码全端共用**：Web、uniapp H5、微信小程序都只传 `images[]`，不存在 canvas 平台差异。
3. **工程质量好**：sharp 原生处理 EXIF 旋转、JPEG 质量、缩放，比手写 canvas 稳。
4. **保留演进空间**：将来若想改方案 C（多图直传），只是后端把 `images[]` 直接转发给 provider，接口契约不变。

> 备选方案 B 可作为「离线/纯前端」降级路径记录，首版不实现。
> 方案 C 作为 §7 的后续优化选项。

## 4. 详细设计

### 4.1 接口设计

#### 复用并扩展 `POST /api/analyze`（向后兼容）

- **单图模式（不变）**：请求体 `{ imageBase64, mimeType, language, subjectId }` → 走原逻辑。
- **多图模式（新增）**：请求体

```jsonc
{
  "images": [
    { "base64": "<raw base64 或 data URL>", "mimeType": "image/jpeg" },
    { "base64": "…", "mimeType": "image/jpeg" }
  ],
  "language": "zh",
  "subjectId": "…",
  "multiStitched": true   // 可选：便于日志/统计标记
}
```

- 后端处理顺序：
  1. 校验：数量 ≤ 5、每张格式白名单（jpeg/png/webp）、单张解码后 ≤ 5MB；
  2. **拼接**：统一宽度 1400px、纵向堆叠、白底、无缝，总高超 12000px 时按比例缩宽度，缩到 640px 仍超 → 400 报错；
  3. 校验拼接结果 ≤ 8MB（解码后），超出降低 JPEG 质量重试；
  4. 调用现有 `aiService.analyzeImage(mergedBase64, 'image/jpeg', ...)`；
  5. 返回 `ParsedQuestion`（同现有 `AnalyzeResponse`）。

- **返回合并图**：响应增加可选字段 `mergedImageBase64`，供前端校对页展示/保存原图（避免前端二次拼图）。
  单图模式不返回该字段（仍用前端已有的 `currentImage`）。

#### 复用但不动

- `POST /api/analyze/detect`：仅单图模式使用，多图模式不调用。
- `shared/src/ai/*`：签名、prompt、schema 均不改。

### 4.2 拼接算法（服务端 `src/lib/image-stitch.ts`，sharp）

```text
输入 images[]
→ 每张 sharp().rotate()（自动 EXIF 旋转）.resize({ width: 1400, withoutEnlargement: true })
→ 计算各张新高度，总高 = sum + (n-1)*gap（gap=0，首版无缝）
→ 若总高 > 12000 → 等比缩宽度重算，直到 640px 下限
→ 创建 white 底画布 width=1400, height=总高
→ 依次 composite 到纵向 offset
→ toBuffer JPEG quality 自适应（≤8MB）
→ 返回 { base64, width, height }
```

> 依赖：新增 `sharp` 到 `@grow/shared` 或学习端 `src/lib`（需评估部署镜像体积；sharp 已是常见依赖，Docker 多阶段构建无额外风险）。
> 备选：若不想引入 native 依赖，可用 `jimp`（纯 JS）替代，性能略低但体积更小。

### 4.3 前端改动（按文件）

#### Web（`src/`）

| 文件 | 改动 |
|---|---|

| `src/app/api/analyze/route.ts` | 支持 `images[]` 分支 + 上述校验 + 调拼接工具；单图分支不动；多图分支沿用限流 |

#### uniapp（`uniapp/src/`）

| 文件 | 改动 |

## 5. 边界与风险

| 风险/边界 | 说明 | 对策 |
|---|---|---|
| 合并图 token 预算 | 超高长图可能超过视觉模型上下文（gpt-4o ~12000 token / Gemini tile 计费） | 总高 ≤ 12000px、宽度 1400px 是保守安全线；后续可用方案 C 多图直传规避 |
| 浏览器/小程序侧无拼接压力 | 服务端拼，客户端只需展示缩略图 | 无 canvas 尺寸风险 |
| sharp native 依赖 | 增加镜像体积/构建复杂度 | 评估；备选 jimp |
| 请求体积 | 多张 raw base64 上传体积增大 | 前端每张仍先 `processImageFile` 压缩到 ≤1MB 再传；单张上限 5MB 兜底 |
| 拍照方向/阴影 | 接缝处可能出现白缝/黑边 | sharp `.rotate()` 处理 EXIF；白底填充；首版无缝，接缝问题靠 prompt 忽略（可选） |
| 顺序错误 | 用户传图顺序与卷面顺序不一致 | 前端支持拖拽/上移下移调整，顺序即拼接顺序 |
| 单图回归 | 改动可能影响现有单图流 | 验收用例强制回归 detect/框选/识别链路 |

---

## 6. 验收标准

1. Web 端多选 ≥2 张 → 缩略图可排序/删除/追加 → 合并识别出一整道题 → 校对页展示合并原图 → 保存后详情原图正确。
2. 只选 1 张 → 与现状完全一致（题目定位、框选、识别、保存）。
3. 张数 > 5、单张 > 5MB、拼接后超高/超体积，均有明确中文提示，不卡死。
4. 多图模式下不再走 detect/框选，直接进入识别。
5. uniapp H5 多选 + 合并识别可用；小程序入口可调同一接口（若小程序本期不做则标记为规划）。
6. 后端日志能区分单图与多图（multiStitched / images.length）。
7. 单图路径自动化测试（现有 Vitest/Playwright）全部通过；新增拼接工具单测。
